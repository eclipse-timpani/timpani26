## 1. Purpose and Applicability Rules

This document specifies only the software requirements needed to achieve **Phase 0 (basic chain operation verification)** of the Data-Driven Workload defined in [REQ-009](REQ-009-data-driven-workload.md). The Phase 1 requirements (`Activation Window` control, offline E2E verification, and successful runtime updates of tables that contain a Pipeline) and the Phase 2 requirements (`SKIP` reporting for missing input, `DATA_TIMEOUT` reporting, and safe initialization of abnormal-state recovery) are not automatically inherited through this document.

Requirement IDs use the `REQ-DD-P0-F-###` (functional) and `REQ-DD-P0-N-###` (non-functional) prefixes to distinguish them from the full-phase requirements (`REQ-DD-###`). All active entries in the tables are **SHALL** requirements (mandatory) within the Phase 0 scope. Mapping to the compound-phase parent requirements (`REQ-DD-001`, `002`, `009`, `015`, `013`) is **limited to the Phase 0 applicability specified in [REQ-009](REQ-009-data-driven-workload.md) §1.5.3** and does not signify completion of the corresponding parent IDs in their entirety.

## 2. Phase 0 Test Boundary

| Category | Phase 0 Condition |
|:---|:---|
| **Execution Target** | Connect Tasks whose original `TemporalClass` is L1 TT or L2 CBS into the same DAG on a single node. Do not change the execution layer according to the DAG role. |
| **Chain Composition** | Use a basic chain with the same period and combinations of mixed L1/L2 Tasks. Each Task retains the TT timing or CBS timing of its existing layer. |
| **Time and State Baseline** | Use a fixed `E/H/table`. `ALL` creates a common ready state. L1 executes in an allowed TT slot, and L2 executes at a CBS release/gate. The ready state is consumed atomically exactly once. |
| **Initial Attach Boundary** | In normal Phase 0 startup (including the order of `/proc` discovery followed by SHM publication), all Successors complete `ttsched_init()` before the first dispatch. A call made while SHM is not yet published is recorded with `g_attached_before_publish = 1`, preserving token `0` by securing cursor `0` upon entry into the first valid generation. A late attach when the already-stable publication has `cur = N > 0` is limited to that node's own `0..N-1` non-replay boundary test (resynchronization of downstream `ready_sequence` across multiple hops is deferred to Phase 2 `REQ-DD-014`). The Source wake delay is assumed to satisfy `wake_delay < Source_period`. |
| **Payload Ownership and Lifetime** | The payload is application-owned. The Producer calls `signal_ready(token)` only after completing publication of the token-addressed payload, and does not overwrite it before the Consumer completes processing. 009 does not define or verify payload location, structure, or an acknowledgment API. |
| **SHM Writer Trust Boundary** | `O_RDWR` is a mapping of the entire `/timpani_ttsched` object. Phase 0's `timpani-pub` includes only mutually trusted cooperative writers, while untrusted workloads use only the read-only group. Isolation against a malicious writer at the slot/header level is not guaranteed. |
| **Runtime-Update Boundary** | Do **not** perform runtime updates (`UPD-REPLACE / ADD / REMOVE / CLEAR`) of tables that contain a Pipeline during testing (deferred to Phase 1). However, verification of stable publication at `/timpani_ttsched` and non-execution of the control wake ([DDR-011](DDR-011-runtime-table-update.md) `D-P0-05`) is mandatory, as is regression prevention for successful Phase 0 updates of ordinary TT tables that do not contain a Pipeline under [REQ-011](REQ-011-runtime-table-update.md). |
| **Inputs and Responsibilities** | Submit the DAG through `Timpani-O` input (or a test-input path), and allow only `Timpani-O` to validate and generate it and transmit it through the existing `O → N` path. Do not determine End-to-End success solely from `Timpani-N` or direct SHM injection. |
| **Interface and Approval Constraints** | Preserve existing public C++ methods, the initial `timpani_task_slot` layout, and the `void ttsched_init()` signature. The `.proto` extension has an 008-aligned allocation proposal (`OI-DD-01`: `TaskInfo` fields 11/12/13), but the field-12 presence semantics and schema incorporation still require `CON-DD-05` approval. Reflect the backward SHM extension and new public `libttsched` APIs (`OI-DD-02`) in code only after Project Leader approval and finalization of all conditions. |

Harmonic multi-period operation, precise time windows by layer, quantitative `E2E Feasibility`, `SKIP`, and `DATA_TIMEOUT` are outside the Phase 0 scope. CPU/slot placement in Phase 0 uses the existing TT or CBS scheduler policy.

## 3. Functional Requirements (Phase 0 Functional Requirements)

### 3.1 Input, Generation, and Pre-Rejection (`Timpani-O` & `Timpani-N`)

| ID | Requirement Specification | Parent REQ | REQ Acceptance Criteria |
|:---|:---|:---|:---|
| **REQ-DD-P0-F-001** | Only `Timpani-O` shall interpret and validate predecessor dependencies in the form `TaskReference(workload_id, task_id)` (`TaskReference.task_id` shall exactly match `TaskInfo.name` (field 1) in a `1:1` relationship). An empty `workload_id` shall be normalized to the current workload, and references to another workload shall be rejected in Phase 0. ### 3.2 Runtime `Data-Ready` Synchronization and Scheduling Enforcement (`Timpani-N` & `libttsched`)

| ID | Requirement Specification | Parent REQ | REQ Acceptance Criteria |

| **REQ-DD-P0-F-004** | An L1 Source shall have `Timer Master` determine the single common `base_cycle_start` at `start()` and the Source-specific Pipeline-period activation ordinal `k`. An L2 CBS Source shall have an `O_RDWR` event adapter/test generator record `k` in the Source slot's `ready_state` with a release-valid marker by calling `ttsched_release_source(task_name, k)` (with mandatory validation of `execution_model == TIMPANI_EXEC_CBS`), and then wake the Task. A Successor shall satisfy both `ALL` ready for one active chain-job token and its layer-specific dispatch gate. A publication, shutdown, or generation-change control wake shall stop with `ESTALE`, while a spurious wake with unchanged generation and state shall wait again with `0` executions. | REQ-DD-002, 004, 005 | AC-DD-P0-01, AC-DD-P0-02 |
| **REQ-DD-P0-F-005** | A Producer shall call `signal_ready(token)` only after completing the token-addressed payload publication and required release ordering. `signal_ready(job_token)` shall verify the `g_shm_generation` match inside the publication commit guard (`ESTALE` immediately when `g_shm_generation != 0U && gen != g_shm_generation`), validate its own slot identity by `n_tasks` range and a 16-byte atomic name comparison (`atomic_name_equals`), and then snapshot and validate the complete outgoing-edge list and preflight every destination before the first `ready_state` change. After the first CAS begins, atomic rollback/retry against a Source process crash is not guaranteed in Phase 0; if it occurs, the chain run shall be treated as failed. A direct duplicate returns `EALREADY`; another token returns `ESTALE`. | **REQ-DD-P0-F-006** | The existing `void ttsched_init(void)` signature shall be retained, with `g_shm_init_errno` and full TLS bulk reset introduced. For an attach to an already-stably-published `cur = N > 0`, it shall snapshot `g_last_dispatch_counter = N` and not replay `0..N-1`. `wait_data()` shall consume only after the attach cursor, in sequential FIFO order (`g_last_dispatch_counter++`); a spurious `FUTEX_WAIT` wakeup with unchanged generation and state shall wait again with `0` executions, while a control wake or generation change shall stop with `ESTALE`. For an L2 Successor, only the `ALL` fan-out commit whose complete outgoing-edge CAS has finished shall increment `dispatch_counter` by 1 and wake it; thereafter, only the BPF CBS CPU/budget/Gap gates determine actual execution. | REQ-DD-008, 009 | AC-DD-P0-01, AC-DD-P0-05 |

### 3.3 Test Observation and Handling of Departures from Assumptions

| ID | Requirement Specification | Parent REQ | REQ Acceptance Criteria |
|:---|:---|:---|:---|
| **REQ-DD-P0-F-008** | Test logs shall correlate the table identifier, job token, payload generation/token, Task-specific start and completion `CLOCK_MONOTONIC` timestamps, `ttsched_signal_ready()` duration, and the pre-rejection reason. Duplicate-token/token-mismatch rejection shall record `EALREADY`/`ESTALE`. If a Source process crash is observed after the first CAS, the point where a partial commit is possible shall be recorded and the chain run shall be treated as failed; it shall not be judged a successful automatic rollback/retry. If a Phase 0 test assumption is violated, such as disconnected operation or a clock anomaly, the test shall be aborted rather than judged successful, and the cause shall be recorded; it shall not be assumed that automatic recovery or timeout `SKIP` operates. | REQ-DD-013 | AC-DD-P0-01..06 |

## 4. Non-Functional Requirements (Phase 0 Non-Functional Requirements)

| ID | Requirement Specification | Parent REQ | REQ Acceptance Criteria |
|:---|:---|:---|:---|
| **REQ-DD-P0-N-001** | Dynamic memory allocation, blocking IPC/gRPC, data-file/network I/O, **`shm_open`/`fstat`/`close` VFS/fd system calls**, unbounded busy-spin, or blocking locks shall not be added to the modified RT critical paths (`Timer Master` loop, `libttsched` `release_source`/`signal_ready`/`wait_data`/`current_job_token` paths, and `scx_timpani` callbacks). | **REQ-DD-P0-N-004** | Interface changes shall be incorporated after approval, and inputs exceeding the TT/CBS/SHM/edge limits shall be rejected in advance. | REQ-DD-001, 015, CON-DD-05, CON-DD-06 | AC-DD-P0-04, AC-DD-P0-05 |
