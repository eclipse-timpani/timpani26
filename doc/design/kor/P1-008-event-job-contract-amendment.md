# Event-Driven Workload Support — P1 계약 보강 합의

**날짜:** 2026-11-11

**상태:** 사용자와 합의한 P1 수정 방향. 상세 설계·API·구현 방식은 후속 검토 대상.

**기준:** `9209bc5`의 008 설계에 대한 변경 요구를 기록한다. 정본 REQ/SRS/DDR/HLD/LLD 전체에 반영 완료된 상태는 아니다.

**추적:** [기능 지원 Issue #53](https://github.com/eclipse-timpani/timpani26/issues/53). 설계 Draft PR은 검토용이며, 설계 병합만으로 기능 구현·검증 완료를 의미하거나 기능 Issue를 종료하지 않는다.

## 1. 합의한 목표

> 앱이 명시적으로 연결한 Event 한 건마다 독립된 Job 한 건을 만들고, 해당 Event의 도달 시각을 기준으로 마감을 정한다. 마감까지 완료되지 않으면 Job의 실행·스로틀·완료 여부와 무관하게 마감 실패를 감지한다. 이벤트 데이터와 식별·시각 정보는 통지·소비·복구 과정에서 일관되게 연결되어야 한다.

| 합의 | P1에서 요구하는 동작 |
|:--|:--|
| **한 Event–한 Job** | 수락한 각 Event는 독립된 Job으로 처리한다. pending Event를 모두 하나의 Job으로 합치지 않는다. 처리 전 폐기·취소는 완료가 아닌 별도 결과로 기록한다 |
| **마감 경과 시 감지** | Job 완료 콜백을 기다리지 않는다. 큐 대기·실행·선점·예산 소진에 따른 실행 보류 중에도 기한 초과를 감지한다 |
| **큐·통지·복구의 공통 계약** | 데이터와 Event 식별자·도달 시각이 어긋나지 않도록 수락·거절·넘침·재등록·재시작 규약을 정의한다 |

## 2. 시각과 마감의 의미

| 표기 | 뜻 |
|:--|:--|
| 도달 시각 | 앱의 입력 어댑터가 선언한 경계에서 Event 한 건을 인지한 시각. 원격 송신·물리적 센서 발생 시각과는 구분 |
| 활성화 시각 | 해당 Event의 Job이 실행 가능해진 시각. 워커가 이미 실행 중이면 새로운 커널 Runnable 전환은 없을 수 있음 |
| 최초 실행·처리 시작 | 커널의 워커 실행과 앱의 Job 시작을 구분하여 연결한다. 실제 기록 수단은 상세 설계 대상 |
| 완료 시각 | 선언한 처리와 결과 게시를 마친 시각. 네트워크 전달·장치 반영 완료를 자동으로 뜻하지 않음 |
| D | Relative deadline — 상대 마감시간. 도달부터 완료까지 허용되는 경과시간 |

**절대 마감 = 해당 Event의 도달 시각 + D**다. 수락·활성화·보충·재개가 늦어져도 마감을 뒤로 옮기지 않는다. 활성화 시각 + D는 대체 마감으로 사용하지 않는다.

- 완료 시각이 절대 마감 이하이면 마감 충족이다.
- 완료 시각이 절대 마감보다 늦거나, 마감이 지난 시점까지 완료되지 않았으면 마감 실패다.
- 완료와 타이머 처리가 경합해도 실제 완료 시각을 기준으로 판정한다. 수집이 늦었다는 이유만으로 정시 완료를 실패로 판정하지 않는다.
- 마감 실패 감지는 Job당 한 번으로 식별한다. 이후 완료는 별도 완료 기록으로 연결하며 실패를 중복 계수하지 않는다.
- 마감 전에 명시적으로 폐기·취소한 항목은 성공 완료가 아니다. 그 항목의 마감 감시를 종료할 조건과 정책적 폐기 결과를 명시한다. 이미 발생한 실패를 취소로 지우지 않는다.

## 3. 명시적 연결 계약과 책임

앱은 Event의 의미와 수신 경계를 정한다. TIMPANI가 임의의 `recv()`·`read()`·커널 깨움에서 메시지 의미를 자동 추론하지 않는다.

| 주체 | 필요한 책임 |
|:--|:--|
| 입력 어댑터 | 발생원, Event 식별자·도달 시각, 대상 워커 및 데이터 항목을 연결하여 전달 |
| 공통 이벤트 전달 경로 | 수락 여부를 확정하고, 수락한 Event의 데이터·메타데이터가 소비 전에 일관되게 게시되도록 보장 |
| 워커 | 한 번에 Event 한 건을 소비하는 Job을 시작하고 명시적으로 완료. 수면 없이 이어지는 Job도 경계를 전달 |
| TIMPANI | 발생원–워커–실제 스레드 연결, Job 식별·기한 관리, CPU 예산 집행, 실행 상태 관측, 마감 실패 감지·보고 |

각 Event/Job의 식별에는 발생원 내 순번과 등록 세대 등 오래된 정보와 새 정보를 구별할 수단이 필요하다. 자료구조와 실제 필드는 후속 설계에서 결정한다.

수락한 Event는 **대기 → 처리 중 → 완료 / 명시적 폐기·취소**로 추적한다. 마감 실패는 처리 상태와 별도의 결과다. 실패한 Job을 계속 실행할지 취소할지는 별도 정책이며, 실패 감지가 자동 종료를 뜻하지 않는다.

커널 관측만으로 등록한 기존 워커에는 CPU 예산 집행·실행 관측을 제공할 수 있다. 그러나 명시적 Event 연결이 없으면 이 문서의 **Event별 도달 기준 마감 지원과 동등하다고 설명하지 않는다.**

## 4. 완료를 기다리지 않는 감지에 필요한 설계

- 첫 수락 시점부터 각 Event/Job의 절대 마감을 감시 대상에 넣어야 한다. 워커가 시작해야 감시를 시작하는 방식은 불충분하다.
- 완료·폐기·취소와 기한 경과 처리는 동일한 식별자와 세대를 사용하여 경합·중복을 해소해야 한다.
- CPU가 유휴이거나 워커가 스로틀되어도 감지가 동작해야 한다.
- **기한 경과부터 감지까지의 허용 지연**과 **감지부터 외부 보고까지의 지연**을 각각 정하고 측정해야 한다. “마감 경과 시”는 지연 0을 보장한다는 뜻이 아니다. 수치는 아직 합의하지 않았다.
- 감지 타이머·공유 정보 전달 수단·실시간 경로 비용은 Linux 타깃에서 검증한다. 기존 Replenisher가 이 기능을 이미 제공한다고 가정하지 않는다.
- 데이터와 메타데이터 저장 공간에 상한을 두고, 가득 찼을 때 수락 거절 또는 명시적 폐기 정책을 정의한다. 무한 대기열을 가정하지 않는다.

기존 CPU별 예산 집행·FIFO(First In, First Out — 활성화 순서 우선)·BPF 중심 예산 소유권은 기반으로 유지하되, 새 Job 경계와 결합했을 때의 보충·과부하 동작 및 승인식은 재검증한다. **Job을 새로 만든다는 이유만으로 예산을 새로 주지 않는다.** 공개 API·프로토콜 변경은 별도 검토·승인 대상으로 남긴다.

## 6. 필수 검증 시나리오

- 정상 Event마다 독립 Job과 고정된 도달 기준 마감이 생성된다.
- Job A 처리 중 Event B가 도달해도 A의 마감이 B의 시각으로 바뀌지 않는다.
- 수면 없이 A 다음 B를 처리해도 서로 다른 Job으로 기록·판정된다.
- 워커가 실행을 시작하지 못하거나 예산 소진으로 대기해도 마감 실패가 허용 지연 안에 감지된다.
- 완료 통지가 늦게 수집되어도 실제 정시 완료를 오판하지 않는다. 완료·타이머 경합 시 실패는 중복되지 않는다.
- 큐 게시·통지·수락 거절 경합과 재시작 경계에서 다른 Event의 데이터를 처리하지 않는다.
- 이전 등록의 타이머·완료·종료 정보가 새 등록 상태를 변경하지 않는다.
- SOME/IP FCW와 비-SOME/IP 앱이 같은 계약을 사용하고, 한 앱의 폭주·과실행 시 다른 앱에 대한 간섭을 보완된 승인 기준으로 확인한다.
